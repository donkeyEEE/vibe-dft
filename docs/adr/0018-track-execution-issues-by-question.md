# 以问题语义组织执行中发现的 Issue

## 背景与取舍

计算归属树表达 RQ、Spec、Task、Run 的工作归属。执行中值得后续调查的问题可能连接
多个 RQ 和 Spec；若只保存在单次任务日志，相关现象容易被割裂。把所有异常转成
Issue 又会增加维护负担。因此以较高门槛记录独立问题，并放宽有依据的聚合门槛。

## 决定

- 新增 calc-issue。执行中有具体证据、有探究价值且需要独立跟踪时，自主轻量记录并
  汇报告知；普通执行排障继续由 calc-execute 处理。
- Issue 存放在维护主线的 04-问题排查/，使用项目内唯一、递增、不复用的 ISSUE-NNN
  加简短主题命名。对应关系由 Issue 内的关联对象与证据维护，路径保留完整对象归属。
- 有合理潜在联系即可先聚合、后分化，不要求先证明共同原因，不建立上位 Issue。
  合并保留来源证据及跳转，后续统一推进保留对象。
- 生命周期仅有待探究、探究中、已完成。等待验证仍为探究中；暂缓回到待探究。
  合并以去向记录，不冒充完成。反证推翻结论时重开并标注受影响经验待复核。
- 后续探究默认等待用户委托，也可事先授权。推进以调研为主；新增验证先记录并汇报
  向对应 RQ 补充 Spec 或向对应 Spec 补充 Task 的需求。有明确设计授权才交接
  calc-to-spec，必要计算由既有计算工作流承接。
- 问题回答充分且可复用经验已沉淀才完成。经验是否有价值取决于对未来工作有无帮助，
  可来自调研，需注明来源、适用范围与验证情况；不强制新 RQ 或经验的产出数量。
- 新 RQ 的创建仍遵循 calc-rq 的批准流程。本决定补充 ADR-0017 中暂缓讨论的发现入口，
  不扩大原有 RQ 边界或把 Issue 委托视为计算设计与执行授权。

## 本次范围

实现 Issue 记录、调研、关联和需求交接。当前回答与经验内容保留在 Issue 内。
独立经验存储、复用维护及插件知识更新另行讨论；本次不引入此类机制。
Spec 和 RQ 保持既有权威，Issue 关联不自动产生依赖、改变验收或接管进度跟踪表。
