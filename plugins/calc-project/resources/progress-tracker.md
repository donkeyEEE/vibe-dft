# 进度跟踪表契约

## 职责与旧项目

每个 RQ 在 `RQ.md` 同级保存一份 `tracker.json`，只记录该 RQ 及其 Spec、Task、Run。
项目总览按配置的 `RQ location:` 枚举 RQ 目录并汇总各表，不维护项目级跟踪表。
`calc-setup` 拥有项目 AGENTS 维护约定的写入和迁移，遵循其现有授权规则。
其他技能直接维护派生跟踪表；项目约定缺失时使用本契约处理跟踪表，
将稳定项目规则的补齐交给 `$calc-setup`，不自行修改项目 `AGENTS.md`。
`show-cot` 可以继续查询或重建跟踪表，并说明项目规则尚待配置；规则补齐不作为查询的前置条件。
首次创建某 RQ 的跟踪表时，在根 `.gitignore` 追加该文件的精确项目相对忽略规则
（以 `/` 开头，例如 `/01-main/01-rqs/RQ-001-example/tracker.json`），保留其他规则。

## 项目 AGENTS 约定

由 `calc-setup` 在初始化或维护项目时，将以下约定写入项目 `AGENTS.md`，保留其他项目规则：

> **进度跟踪表维护**：每个 RQ 目录下的 `tracker.json` 是该 RQ → Spec → Task → Run 的派生摘要。
> 四类对象中任一对象的状态发生改变，都必须在写入权威记录后立即直接更新所属 RQ 的跟踪表，
> 并检查两者一致，完成后再继续执行或交接。新增、删除、重命名、归属或路径变化，以及 current Run
> 切换时也同步维护；跨 RQ 移动对象时更新源和目标两份表。以 RQ.md 和 Spec 为权威，保留无关条目；
> 索引更新失败时明确报告未同步，在恢复工作时优先修复。由智能体直接编辑 JSON，无需统一更新脚本。
> 某份跟踪表缺失或损坏时，仅从该 RQ.md 及其已发布 Spec 重建该表；日常只更新受影响 RQ。
> 同一 RQ 存在其他写入者时，写入前重读最新跟踪表并合并各分支变更，避免覆盖他人更新。
>
> 每份跟踪表顶层使用 `schema_version: 1`、`updated_at`（含时区的更新时间）和单个 `rq` 对象。
> `rq` 包含 `id`、`title`、`status`、`source`（项目相对 RQ.md 路径）及 `specs` 数组；
> Spec 条目包含 `id`、`title`、`status`、`source`（项目相对 Spec 路径）及 `tasks` 数组；
> Task 条目包含 `id`、`title`、`status` 及 `runs` 数组；Run 条目包含 `id`、`status` 和布尔值 `current`。
> 各层空子集合写为 `[]`；ID 仅在父范围内唯一，以 RQ 的 source 和完整父链定位条目。
> 状态照录权威记录，不通过子对象状态推断父对象状态，不复制科学正文或执行日志。
> 查询单个 RQ 只读其跟踪表；项目 COT 枚举配置范围内的 RQ 目录并汇总各表，不保存重复的项目级状态表。
> 仅在缺失、异常、已知未同步或用户要求核对时回查相应 RQ 的权威记录。

空项目不创建跟踪表；创建 RQ 时建立其跟踪表，尚无 Spec 时 `rq.specs` 为 `[]`。
某 RQ 的跟踪表覆盖该 RQ 的全部已发布 Spec 后才能视为完整；无法读取的记录应报告为未完成重建。
项目总览以配置范围内实际 RQ 目录为覆盖依据，不能仅搜索现有 `tracker.json` 而遗漏尚未建表的 RQ。

## 从项目级跟踪表迁移

旧项目存在 `.calc-project/tracker.json` 时，`calc-setup` 在获准维护的范围内，从各 RQ 权威记录
分别建立并核实 RQ 内的跟踪表，更新项目 AGENTS 约定及忽略规则；全部完成后删除旧项目级派生表。
迁移未完成时保留旧文件并报告未完成项，日常查询与状态维护仍使用 RQ 内的表，不回退到旧项目表。
保留 `.calc-project/` 内的其他文件及其报告忽略规则。
