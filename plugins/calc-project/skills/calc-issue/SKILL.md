# Calc Issue

Issue 是执行的附加产物，以问题语义跨 RQ、Spec、Task 组织证据。本接口拥有问题记录、
关联和三状态生命周期；Spec 保持计算设计、Task、Run 及验收权威。
按用户意图选择记录、查询维护或推进入口；仅记录、查询、关联或重开不授权后续探究。
涉及 Calc Project 稳定术语或对象边界时，读取[共享领域术语](../../resources/project-context.md)。

## 定位与记录

1. 解析唯一计算项目，读取其 AGENTS.md、CONTEXT.md、ARCHITECTURE.md。以
   [Issue 记录契约](references/issue-record.md)定位研究主线的 04-问题排查/，
   按项目内唯一 ISSUE-NNN 或路径解析对象。查询时返回问题、状态、关联和未决事项即可。
2. 执行发现同时具备具体证据、探究价值和独立跟踪需要时才创建：它应超出当前 Task 的
   正常分析与验收，值得后续投入。日常报错、直接可解释的差异保留在执行记录中；
   结果不符合预期本身不足以创建。无需为了产生 Issue 追加检查，也无数量配额。
3. 先搜索项目各主线的既有 Issue。采用先聚合、后分化：有合理潜在联系即可纳入同一
   Issue，说明怀疑的联系并分别保留观察与解释，不要求先证明共同原因。需要合并或
   拆分时遵循记录契约；只建立普通关联，不建立上位 Issue 或父子层级。
4. 新建或补充问题、价值、触发证据和关联作用。已委托执行 Spec 时可自主轻量记录，
   无需另行确认；写后核实编号、引用及无重复内容，在执行汇报中告知并交回原任务。
   影响当前计算有效性或验收的异常仍交 calc-execute 即时处理，Issue 不替代排障。

## 调研推进

1. 用户委托推进该 Issue，或已有覆盖它的事先授权时，将待探究置为探究中。
   读取关联的 RQ、Spec、Task 与必要 Run 证据，明确要回答的问题、已有解释和缺口。
2. 以调研为主，利用已有计算证据与可靠原始来源区分解释。可用
   `$dev-engineering:research` 调查具体问题；把返回的来源、实际支持的认识及局限写入
   Issue，区分事实、假设与验证情况。文献支持的有用认识不必一律经本项目计算验证。
3. 需要计算验证时，在 Issue 中记录验证什么、为什么必要、希望区分什么解释、对应
   RQ 或 Spec，以及是补充 Spec 还是补充 Task。先汇报需求；已有明确授权时才交接
   `$calc-to-spec`，由其完成新 Spec 或安全替换现有 Spec 的设计。仅推进 Issue
   不授权修改科学设计或提交新计算。新 RQ 提案交 `$calc-rq`，保留其创建批准要求。
   接收方完成后将实际 Spec/Task 或 RQ 路径补入关联；尚未落实时标为待安排。
4. 必要验证未返回时保持探究中，记录所等结果；本次调用可交还控制，不空转等待。
   返回证据后继续评估。可选拓展不阻止已有问题完成。暂缓或停止投入回到待探究，
   写明原因及恢复条件，不把未回答记为完成。
5. 问题回答充分且其中有复用价值的经验已沉淀时置为已完成。经验以对未来工作有帮助
   为标准，明确认识或做法、来源、适用范围及验证情况；不强求每个 Issue 产出经验
   或新 RQ。当前将回答及经验内容保留在 Issue 的结论与成果中；独立经验存储、复用
   机制和插件知识更新另行设计，本接口不自动创建这类机制或回写插件。
6. 新证据推翻回答时，保留旧结论与证据并标记失效范围，关联的受影响经验标为待复核；
   回到待探究，有继续探究授权时进入探究中。Spec/Task 的状态影响交对应工作流判断。
   每次实质更新后重读记录，报告状态、结论、实际成果与未决验证需求。
