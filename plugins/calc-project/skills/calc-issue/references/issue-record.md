# Issue 记录契约

## 位置、编号与调用

文件位于 `<project-root>/01<main-line-slug>/04-问题排查/ISSUE-NNN-简短主题.md`。
主线位置来自项目结构与 RQ 存储配置；新问题通常由触发它的研究主线维护，已有问题保留
维护归属。文件可跨主线引用证据。目录按首个 Issue 的需要创建，不创建项目级 issues/。

ISSUE-NNN 在整个计算项目内唯一、递增且不复用，至少三位补零。分配前扫描项目各主线
04-问题排查/ 中的 Issue（包括合并来源、历史记录及路径跳转），取已用最大编号加一。
按编号定位和检查唯一性时，先解析下述 Redirect to 跳转并按最终路径去重；
同号的多个独立正式记录仍为冲突。写入前重新检查目标及全项目编号冲突，以新文件创建
而非覆盖。遇到冲突停止该写入并报告路径，不在多个对象中猜选。不另建编号 registry 或关联表。

标题写完整疑问，文件名用简短主题，例如 ISSUE-001-磁态能量排序差异.md。
默认保持文件名和位置稳定；标题或探究范围变化不换编号。确需移动或改名时修复已知引用，
旧路径仅保留编号和 `Redirect to:` 字段（值为指向新相对路径的 Markdown 链接），作为同一对象的路径别名，
不含独立 Status。跳转必须保持同一编号、最终到达一份正式记录，且无环；断链、异号
或环先报告并澄清。跳转保留编号占用，但不作为第二份正式记录。
同一项目中“推进 ISSUE-001”“关联到 ISSUE-001”即可定位。

## 关联对象与证据

由 Issue 文件中的表格维护对应关系，引用相对 Issue 文件的实际路径。
Spec/Task 编号只在父对象内唯一：Task 必须带所属 Spec 路径和 Task ID，
必要时附 Run ID 与具体结果或日志路径。每条关联说明问题来源、相关现象、支持、
反例或验证作用。Issue 间关联使用编号和路径，不表达父子归属或执行依赖。
Issue 发起的新 Spec 或验证 Task 必须在其设计来源中回链，写明来源 Issue 编号、
相对路径及验证目的；由 calc-to-spec 修改设计。整份 Spec 都服务于同一 Issue 时，
在 Spec 层记录；仅某个 Task 承接验证时，在该 Task 内记录。普通任务无需关联 Issue。
交接完成后，calc-issue 核对设计中的来源回链，并将实际 Spec/Task 引用补入本表；
随后补充验证结果及其对问题的影响。Task 的验收仍由 calc-execute 按 Spec 执行。

创建时采用以下最小结构，替换所有占位内容；后续按需添加探究记录、验证需求、
结论与成果、暂缓说明及合并去向。证据保留来源，不复制大型输出。

```markdown
# ISSUE-001：不同方法为何给出相反的磁态能量排序？

Status: 待探究

## 问题与价值

具体疑问、值得投入的理由，以及超出当前 Task 正常分析的部分。

## 关联对象与证据

| 对象（实际路径及作用域内编号） | 关联作用 | 证据或需求 |
|---|---|---|
| [所属 Spec](../01-rqs/rq-001-example/specs/SPEC-001.md)，TASK-001 / RUN-001 | 问题来源 | 具体观察及结果路径 |
```

## 生命周期

Status 只使用 `待探究 | 探究中 | 已完成`：

- 待探究：已记录，尚未启动，或暂缓后等待恢复。
- 探究中：已委托调研；等待必要验证、整理经验均包含在内。
- 已完成：问题已回答，具有复用价值的经验内容已沉淀；不是停止投入或合并的代称。

获得委托后进入探究中；暂缓回到待探究并说明原因。反证推翻完成结论时恢复待探究，
已有继续探究授权时进入探究中。待验证、暂缓和合并只是内容，不新增状态。
相关 Spec 完成不自动完成 Issue；Issue 完成不修改 Spec/Task 的验收。

## 聚合、合并与分化

潜在联系有合理依据即可聚合，在同一问题下并列保留各现象、来源及竞争解释。
合并选定一个保留对象，将来源记录的证据、未决问题、结论及成果引用汇入它。
新合入的疑问使原完成结论不充分时，按重开规则更新保留对象。

来源文件保留原编号、原始证据与 `Merged into:` 字段（值为指向保留对象的 Markdown 链接），不再独立推进；
其 Status 保留合并时历史值，不将合并伪装为已完成。查询或推进旧编号时先说明去向，
沿合并链接定位保留对象；活动问题发现排除这些来源记录。合并前检查去向不形成环，
后续再合并时可将旧跳转直接指向最终对象，保留原证据。遇到断链或环先报告并澄清。

确有独立问题需分化时，保留原 Issue 的编号及仍承载的问题，为分出的独立问题按创建
门槛分配新编号，互相记录分化原因和证据引用；不建立上位对象。
